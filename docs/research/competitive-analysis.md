# 竞品调研：网页翻译扩展

> 调研时间：2026-09。数据来自各扩展商店页面、官方文档与开源仓库，用户量为商店公开数据的量级估算。

## 1. 市场结论先说

这个赛道**已经很成熟，且有绝对头部**。我们不可能靠"也能翻译网页"赢，只能靠差异化切口进场。

## 2. 头部产品做对了什么

### 沉浸式翻译（第一梯队，必须重点参考）

真正让它赢的不是引擎，是**阅读体验**：

1. **双语对照而非替换**：译文插在原文下方，原文始终可核对。这是它名字和口碑的来源。
2. **智能识别主内容区**：只翻译正文，不动导航栏/侧边栏/页脚，视觉噪音极低。
3. **视口内懒翻译**：长页面不会一次性把全文打给接口，首屏快、配额省。
4. **多引擎自由切换 + 用户自带 Key**：不同场景切不同引擎（DeepL 保真、AI 引擎懂上下文）。
5. **场景纵深**：PDF 保留排版、EPUB、YouTube/Netflix 双语字幕。这是它的护城河，也是最贵的部分。
6. **隐私叙事**：显式承诺"翻译内容零保留、不用于训练"，并把它写进商店页第一屏。

值得学的**产品细节**：

- 快捷键一键切换译文/原文（不是两个操作）
- 每个站点可单独设置"始终翻译 / 从不翻译"
- 译文样式可选（下划线、虚线、模糊、卡片……）适配不同网站视觉
- 悬停翻译：鼠标停在段落上按修饰键即翻，介于整页与划词之间

### 简约翻译 KISS Translator（架构上最值得抄的开源实现）

代码可读，分层清晰，是我们做技术设计时最直接的参照：

- `src/apis/` 每个翻译服务一个适配器，策略模式，新增引擎不动上层
- `src/libs/translatorManager.js` 统一调度，负责批量聚合与队列
- `src/config/rules.js` 规则引擎，按 URL + CSS 选择器决定翻译范围与忽略范围
- 同一套核心同时编译成扩展和油猴脚本
- 支持"自定义接口"：用户写一段 JS hook 定义请求与解析，等于把引擎生态外包给社区

它的**规则订阅**机制尤其聪明：站点适配规则做成可订阅的远程列表，社区共同维护长尾站点兼容性，而不是靠开发者一个个修。

### 值得注意的反面教材

- 多数竞品安装即申请 `<all_urls>`，权限提示劝退一部分用户，且必然触发商店深度审查
- 免费引擎接口不稳定时缺少降级，直接表现为"翻译失败"白屏，用户不知道该换引擎
- 译文样式在深色模式/复杂布局网站下经常错位

## 3. 我们的差异化切口

不做"又一个沉浸式翻译"，选三个头部产品做得不够好、且我们能低成本做好的点：

| 切口                 | 竞品现状                       | 我们的做法                                                                  |
| -------------------- | ------------------------------ | --------------------------------------------------------------------------- |
| **权限最小化**       | 普遍安装即要全站权限           | 默认零网页权限，靠 `activeTab` 按需注入；自动翻译才请求可选权限，关闭即撤回 |
| **免费引擎的可靠性** | 单引擎失败就白屏，用户自己排查 | 引擎降级 + 熔断 + 按引擎限流，失败在段落原位显示可读原因                    |
| **完全开源可自查**   | 头部闭源，隐私承诺只能靠信任   | 全量开源，商店审查与用户都能逐行核对"不上传任何页面内容"                    |

**首期明确不做**（避免和护城河硬碰）：PDF、EPUB、视频字幕、AI 大模型引擎、账号与云同步。
